# 05 — Cross-project subagent spawn + projection

Type: grilling
Status: resolved

## Question

Design area 3's core: when an agent in project A (the consumer) needs to work in project B's repo (the npm module), spawn a live agent node **in B's project canvas** (B owns the session, in B's `cwd`), and render an interactive **projection** of it in A's canvas — a greyed/dotted "foreign" node that can be driven in place, with an optional jump into B's design surface.

Settled (from charter, Q12/Q16/Q17):
- **Where the node lives (Q12=a):** the real node + tmux session live in B's `Project.nodes` (B's `cwd` owns the session). A renders a *projection* of it via a **co-attached viewer** — the same primitive the kanban card modal (`ModalTerminal`) uses to attach a second viewer to one tmux session. B is the single source of truth; A stores no copy (the projection is transient/derived each load from the cross-project `Link` + B's node).
- **Spawn (Q17=a):** extend canvas-control `open-agent` to target another project — `open-agent --project <cwd-or-id>` via the existing skill/shim. The hook server resolves the target project, creates the node in B, launches the agent in B's `cwd`, and writes the cross-project `lineage`/`spawn` `Link` (Q15=b) + A's transient projection as side-effects. Reuses the proven agent→canvas seam; no new injection machinery. Local→local works now; **remote spawn (local→remote, remote→remote) is fog.**
- **Communication (Q16=a):** the spawned session and its spawner learn about each other via a `get-linked-context`-style skill/marker block teaching the agent its links and how to query them through the **existing** `/context-link/` hook-server route. No new injection seam. (A native tool-injection "plugin" upgrade is fog — a graduation candidate if the skill path proves too clunky.)

Resolve:
1. The projection data path: A's canvas renders a "foreign" node derived from a cross-project `Link` (source = A's spawning node, target = `{projectId: B, nodeId}`). Decide how A resolves B's node each render (B's `Project.nodes` is in the `useProjects` store; A reads across projects — the link map is already global in main). Pin that A persists **only the link**, never a copy of B's node.
2. The co-attach mechanics: `ModalTerminal` co-attaches a viewer keyed by `(ClientId, viewerId)`. Decide how a *cross-project canvas node* (not a modal) co-attaches — a new `viewerId` channeling into B's session, rendered in A's canvas with the greyed/dotted visual treatment. Address the seeding question (a co-attach joiner misses tmux's mouse-tracking modes — see `coAttachMouse` / `CO_ATTACH_MOUSE_SEQ` in CLAUDE.md).
3. The visual treatment: the "foreign" node — `<100% opacity` / dotted outline / a badge identifying it as part of project B, with an optional "navigate into B's design surface" affordance. Confirm interaction in place is the primary path (drive it without navigating away) and the jump is secondary.
4. The spawn verb's project resolution: `open-agent --project` must resolve `<cwd-or-id>` to an existing project (reuse `openFolderProject` cwd lookup) and refuse if no such project exists (no silent local fallback — the app's own `requireRemote` refusal pattern is the precedent). Decide auth/identity for the spawned node (does it inherit B's account/permission defaults?).
5. Interactions with the dependency link (04): A may spawn in B *because* A depends on B's change (both a `dependency` and a `lineage` link between the same endpoints). Decide whether the spawn auto-creates the `lineage` link only, and the `dependency` link is authored separately, or whether the spawn offers to establish both.

Invoke `/grilling` and `/domain-modeling`. Depends on the `Link` model (01) and the off-canvas authoring surface (06, since cross-project authoring is off-canvas). Check `src/main/canvas-control-core.ts` (`open-agent` verb), `src/renderer/components/kanban/ModalTerminal.tsx` (co-attach precedent), `src/core/pty-manager.ts` (viewer-id ledger), `src/core/context-link.ts` (route + link map).

Blocked by: 01, 06

## Answer

Grounded in `canvas-control-core.ts` (`open-agent` verb + `buildCanvasControlInstructions`), `ModalTerminal.tsx` (the co-attach precedent), `pty-manager.ts` (`join()` ~L1638, the `(ClientId, viewerId)` ledger, `coAttachMouse`/`CO_ATTACH_MOUSE_SEQ`), `context-link.ts`/`context-link-core.ts` (the `/context-link/` route + link map), `projects.ts` (`openFolderProject` cwd dedupe ~L260), and `Canvas.tsx` (the ephemeral-node merge ~L1334 + the `open-agent` dispatch ~L6857). The subagent/loop "merged at the `<ReactFlow>` prop, never persisted" precedent is `Canvas.tsx`'s `ephemeralNodes`/`allNodes` useMemo (~L1334-1462) and the `flowToNodeStates` persistence boundary (`workspace.ts` ~L1341, which serializes only `NodeKind` values — `subagent`/`loop` are not in `NodeKind` and never round-trip).

### 1. Projection data path — derived ephemeral node, link-only persistence

A's canvas renders the foreign node as a **derived ephemeral node** outside React Flow's `nodes` state, merged at the `<ReactFlow>` prop exactly as subagent/loop cards are (`Canvas.tsx` ~L1460: `allNodes = useMemo(() => ephemeralNodes.length ? [...nodes, ...ephemeralNodes] : nodes, [nodes, ephemeralNodes])`). The precedent is load-bearing: subagent/loop nodes live in a separate `agentNodes`/`loopSig`-driven `useMemo` (~L1334) and are filtered out of `flowToNodeStates` by virtue of their `type` not being a persistable `NodeKind` — so they never dirty the canvas, never serialize to `project.json`, and never enter undo. The projection node follows the same contract.

**Source of truth is the `lineage` Link + B's serialized `Project.nodes`.** The derivation runs in a `useMemo` over (A's `Project.links`, the `useProjects` store's full `projects` array). For each `Link` on A's project where `kind === 'lineage'` and `target.ref === 'xnode'`, A reads across projects: `useProjects.getState().projects.find(p => p.id === link.target.projectId)?.nodes.find(n => n.id === link.target.nodeId)`. That serialized `CanvasNodeState` carries the title/color/agentId/cwd/accountId the projection needs to render and to co-attach. A persists **only the Link** (on A's `Project.links`, per ticket 01's Q-L1=a "all links on SOURCE"); no copy of B's node is written to A's `project.json`. The projection is recomputed each load from the live cross-project read, so a title rename or color change in B is reflected in A on the next store update (B's `Project.nodes` is in the same `useProjects` store, so a `setProjectData`/`commitActiveToStore` on B already invalidates the memo).

**Node id + type.** The projection's React Flow `id` must NOT collide with B's real node id across the merged array (React Flow keys by `id` — a collision would respawn). Use a prefixed id: `xproj-${link.target.projectId}-${link.target.nodeId}`. The `type` is a new render-only kind `'xproject'` (added to the `nodeTypes` registry alongside `subagent`/`loop`, and — like them — absent from `NodeKind` so `flowToNodeStates` never serializes it). The node is `selectable: false` / `draggable: true` (same stance as subagent cards — a rubber-band selection must not sweep foreign nodes into Group/Duplicate/Delete actions that cannot act on them). Drag position is transient (ephemeral position state, same `ephemeralPos` map subagent/loop use).

**Edge.** A lineage edge from A's spawning node (`link.source.nodeId`) to the projection, styled like a control rope (source agent's color, dashed), drawn in the same `ephemeralEdges` array.

### 2. Co-attach mechanics — cross-project canvas viewer

The projection node co-attaches to B's tmux session by **node id** (the `persistKey`), exactly as `ModalTerminal` does — but as a canvas node, not a modal. The viewer-identity seam (`pty-manager.ts` ~L366-394) is the whole mechanism: a `SubKey` is `<ClientId>\x00<viewerId>`, so one `ClientId` (this renderer connection) holds multiple subscribers. `ModalTerminal` mints `viewerId = \`modal-${nodeId}-${Math.random().toString(36).slice(2,8)}\`` (`ModalTerminal.tsx` ~L147). The projection node mints an analogous **`viewerId = \`xproj-${link.target.projectId}-${nodeId}-${rand}\``** and passes it as the trailing arg through `LocalTransport` → preload → `pty:create`/`pty:resize`/`pty:kill`. `join()` (~L1648) adds `subKey(clientId, viewerId)` to `existing.subscribers`; the projection is a distinct subscriber of B's session, voting its own size into `existing.sizes`, and its unmount calls `transport.kill(sessionId, viewerId)` which removes ONLY that `SubKey` (the canvas kill path ~L1387-1391).

**Critical: the projection passes B's project context, not A's.** The `transport.create` call mirrors `TerminalNode.tsx` ~L2485 but with: `persistKey: link.target.nodeId` (B's node id = B's tmux session name), `ownerProjectId: link.target.projectId` (B owns the pane), `cwd: B-node.cwd`, `agentId: B-node.agentId`, `accountId: B-node.accountId`, `sshRemote`/`requireRemote` resolved from B's project (B may be an SSH project — A is not). This is what makes it a co-attach JOIN, not a spawn: `join()` (~L1643) finds `byPersistKey.get(link.target.nodeId)` and returns `fresh: false` with the existing session. If B's session does not yet exist (B's canvas never mounted, or post-reboot), `join()` returns `undefined` and `create()` falls to `spawnNew()` — **the projection must refuse to spawn** (it is a projection, not the owner). Gate this exactly as `requireRemote` does: the projection's create call carries a new `requireExisting` flag (or the projection simply treats `fresh === true` as "session not live yet — show a placeholder plate, retry on B's next mount"). The precedent is `ModalTerminal`'s `res.closed`/`res.unavailable` plates (~L253-263).

**Mouse-tracking seeding.** `join()` sets `coAttachMouse = existing.persistKey ? true : undefined` (~L1675) for tmux-backed sessions. The projection node writes `CO_ATTACH_MOUSE_SEQ` (`'\x1b[?1000h\x1b[?1002h\x1b[?1006h'`, `terminal-config.ts` ~L462) into its fresh xterm when `res.coAttachMouse` is set — byte-identical to `ModalTerminal.tsx` ~L320 (`if (res.coAttachMouse) term.write(CO_ATTACH_MOUSE_SEQ)`). Without this the projection's wheel can't scroll tmux history until a keystroke wakes the app into re-requesting mouse (the documented co-attach gap).

**Screen seeding.** A joiner that did not resize gets `join()`'s `captureForResync` screen + `paneCursor` (~L1692-1697), returned as `PtyCreateResult.screen`/`.cursor`. The projection paints via `seedPaint({ replay: attachReplay({parked:false, fresh:false, hasInitialCommand:false}), screen: res.screen })` → `create-screen` branch (`ModalTerminal.tsx` ~L308-314: `term.write('\x1b[0m' + toXtermText(stripTrailingNewline(res.screen)))` then `term.write(cursorPlacementSeq(res.cursor))`). A resized joiner gets no screen (tmux is redrawing it — ~L1682); the projection's xterm paints whatever tmux sends. This is the same `create-screen` path the kanban card modal uses.

**B not currently loaded/mounted.** The tmux session `nt-<B-nodeId>` exists independently of B's canvas (tmux outlives the app; a background project's sessions are live). The projection co-attaches by `persistKey` regardless of whether B's `TerminalNode` is mounted. If B's node was never spawned (no session), `join()` misses and the projection shows a placeholder (same as `res.unavailable`), then re-attempts when B's canvas mounts and spawns the session (a store subscription or a `B-node-mounted` signal invalidates the projection's lifecycle effect).

### 3. Visual treatment

The projection is interactive in place (the co-attached viewer is a live xterm — drive it without navigating away), with the jump as secondary. CSS/class shape: a new `.xproj-node` class on the node root, applying:
- **`opacity: 0.72`** (or a CSS variable `--xproj-opacity`) — visibly dimmed vs. a native node but fully readable.
- **Dotted outline**: `border: 1.5px dashed var(--xproj-stroke)` where `--xproj-stroke` is B's project color (from `Project.color`), so the lineage is visually apparent.
- **Project badge**: a small pill in the header (`.xproj-node__origin`) showing B's project name + color dot, sourced from `useProjects.getState().projects.find(p => p.id === link.target.projectId).name/.color`.
- **Navigate-into-B affordance**: a header button (icon: `↗` or the project-dot) that calls `openNodeGroupAsCanvas` (ticket 07/09's drill) on the projection, OR — as the simpler secondary — switches the active project to B and `focusNodeById(link.target.nodeId)`. The jump is opt-in; the primary interaction is typing/scrolling in the co-attached xterm.

The node carries the same hover-guard + ResizeObserver + OSC 52 copy pill as `ModalTerminal`/`TerminalNode` (it IS a terminal view). It is excluded from the WebGL budget coordinator's per-node acquire (it can use the DOM renderer, or participate as a normal client — decision deferred to implementation, but it must not be a budget-free second context on top of B's node's context).

### 4. Spawn verb — `--project` resolution + refusal + B-defaults inheritance

Extend `open-agent` in `canvas-control-core.ts`'s `parseControlRequest` (no new validation needed — `--project` is an optional flag) and in `Canvas.tsx`'s `case 'open-agent'` dispatch (~L6857). The `--project <cwd-or-id>` arg resolves to an existing project via the **same cwd lookup `openFolderProject` uses** (`projects.ts` ~L261: `get().projects.find(p => p.cwd === folder)`). Resolution order: (1) if the value matches a `Project.id`, use it; (2) else if it matches a `Project.cwd`, use that project; (3) else **REFUSE** — `reply({ ok: false, error: 'no project found for --project <value>; open the folder first' })`. **No silent local fallback.** The precedent is `PtyCreateOptions.requireRemote` (`pty-manager.ts` ~L1713: a create that would silently land in the wrong context is refused instead). A cross-project spawn that cannot find B must not create the node in A — that would silently violate the "B owns the session" invariant (Q12=a).

**Where the node is created.** The `case 'open-agent'` handler currently operates on the active project's `nodesRef`. With `--project`, it must write into **B's** `Project.nodes` via `useProjects.getState().setProjectData(B.id, nodes => [...nodes, newNode])` (the `mapProjectNodes` helper, `projects.ts` ~L226) rather than the live React Flow `setNodes`. B's canvas is not active, so the node is serialized into B's store and appears when B is next loaded. The node's `cwd` is B's `cwd` (or `--cwd` if given, resolved against B); `agentId`/`--agent` as today.

**Auth/identity inheritance — B's defaults, not A's.** The spawned node is B's node. It inherits:
- `project.defaultAccountId` from **B** (not A's spawner's account) — `resolveNewNodeAccount(undefined, B-project, settings.claudeAccounts)`.
- `project.defaultPermissionMode` from **B** — `activePermissionMode(agentId)` bound to B's project (the resolver reads `project.defaultPermissionMode` → `settings.claudePermissionMode`; for the spawn it must be resolved against B, not the active project).
- `cwd` from B's project root (or `--cwd`).

The spawner in A does NOT impose A's account/permission on B. This mirrors the `ownerProjectId` discipline (`TerminalNode.tsx` ~L2498, `ModalTerminal.tsx` ~L246): the pane-ownership ledger records B's project as the owner, so agent messaging and status routing are correct.

**Side-effects.** After node creation in B, the handler writes the cross-project `lineage` Link on A's `Project.links` via the `commitLinks` funnel (ticket 06): `source = { ref:'node', nodeId: sourceNodeId }` (A's spawning node), `target = { ref:'xnode', projectId: B.id, nodeId: <new B node id> }`. A's transient projection derives from this link on the next render. The agent in B is launched via B's `cwd` (the `initialCommand` → `writeWhenShellReady` path fires when B's canvas loads the node; if B is already active, it fires immediately).

**Communication (Q16=a).** The spawned session + spawner learn about each other through the existing `get-linked-context` skill/marker block and the `/context-link/` route. The `lineage` link is fed into `contextLink.setLinks(map)` so the `/context-link/summary`/`list`/`transcript` verbs resolve the `xnode` endpoint by reading B's node's transcript (the route's `resolveLinkTranscript`, `context-link-core.ts` ~L25, must handle `ref:'xnode'` by looking up B's node + resolving its transcript through B's account/cwd — the cross-project read path the context-link system already needs for ticket 01's endpoint unification). No new injection seam.

### 5. Dependency link (04) — lineage-only spawn, dependency authored separately

Per the default: the spawn auto-creates **only the `lineage` link** (its own bookkeeping — "this node was spawned by that node"). The `dependency` link ("A depends on B's change") is authored **separately** off-canvas via ticket 06's `LinkTargetPicker`/`LinkInspectorPanel` if the user wants to declare it. The spawn may **OFFER** to also establish the dependency link (a reply line: `opened <id> in <B>; also mark A as depending on B's branch? (link --kind dependency …)`) but does not require it.

**Coupling to 04.** 04 leans declarative for the `dependency` link and enabling 05's spawn as an action. This resolution is consistent: the `lineage` link is the spawn's own record (always created), and the `dependency` link is the user's declarative intent (optionally authored). If 04 later decides the spawn should auto-create both, the `commitLinks` call in the `--project` handler is the single funnel to extend (add a second `Link` with `kind:'dependency'`, same endpoints, to the `commitLinks` batch) — no architectural change to the projection or co-attach mechanics. The two links sharing endpoints is already supported by the `Link` model (ticket 01: distinct kinds, two links where both apply, Q15=b).
